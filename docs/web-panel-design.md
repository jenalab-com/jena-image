# 웹 패널 — 사이드바 옆 브라우저

> 2026-11-21 작성. 참고 이미지를 웹에서 찾아 보고 있는 폴더로 바로 모으기 위한 패널이다. 범용 브라우저를 앱 안에 하나 더 두려는 것이 아니다.

## 왜

참고 이미지를 모을 때 지금은 브라우저에서 내려받고 → Finder에서 옮기고 → JenaImage에서 확인한다. 찾는 화면과 모으는 화면이 한 창에 있으면 이 세 걸음이 한 걸음이 된다. 같은 워크스페이스의 `jena-web`(Swift·AppKit + 시스템 WebKit)에 이미 검증된 브라우저 엔진 코드가 있어 그것을 바탕으로 한다.

## 목표 · 하지 않는 것

**목표**

- 툴바의 웹 버튼으로 사이드바와 목록 사이의 패널을 열고 접는다(AI 버튼과 같은 방식).
- 주소·검색 입력, 뒤로·앞으로·새로고침, 로그인이 되는 탭 브라우저(2026-11-22에 "한 페이지"에서 탭으로 넓혔다).
- 웹 이미지를 **우클릭 → 폴더에 저장**, **끌어다 목록·폴더에 놓기**로 저장한다.
- 저장하면 목록이 갱신되고 새 파일이 선택된다.

**하지 않는 것**(작성자 결정: 처음엔 "한 페이지", 써 본 뒤 탭만 더함)

- 파비콘, 북마크, 방문 기록, 개인정보 관리 화면, 사이트별 설정, 탭 단축키(⌘T·⌘W — 창 닫기 계열과 헷갈린다).
- jena-web 저장소 수정. JenaWeb.app과의 로그인 공유(WebKit 저장소가 앱별이라 불가).
- 다른 앱(Safari 등)에서 끌어온 웹 이미지 받기 — 이번 범위 밖. 지금처럼 파일 끌어오기만 받는다.

**이렇게 되면 실패**

- 패널을 붙인 탓에 기존 목록·뷰어·AI 패널 동작이 달라진다.
- 저장했는데 이미지가 아닌 파일(오류 페이지 HTML 등)이 폴더에 남는다.
- 사용자가 고르지 않은 폴더(직전 폴더 등)로 조용히 저장된다.

## 접근

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 옮겨 다듬기** | jena-web의 엔진 코드를 `Sources/web/`로 가져와 패널용으로 줄이고, 화면은 새로 짠다 | **채택** |
| B. 공용 패키지 | 엔진을 Swift 패키지로 뽑아 두 앱이 함께 쓴다 | 두 앱의 빌드 방식이 다르다(jena-image는 `swiftc` 한 번, jena-web은 CMake·Xcode). 엔진이 앱 생명주기·번들 리소스와 얽혀 있어 뽑아내는 일이 본 작업보다 크다. 500줄을 위해 두 저장소를 묶지 않는다 |
| C. JenaWeb.app 연동 | 별도 앱을 띄워 옆에 둔다 | 다른 프로세스의 창은 사이드바에 넣을 수 없고, 폴더 저장 연동에 앱 간 통신이 필요하다 |

A를 고른 이유: jena-web의 창(`BrowserWindowController`)은 독립 창이고 엔진(`WebKitBrowserRuntime`)은 `NSApplicationDelegate`까지 겸한다. jena-image는 모든 소스를 한 모듈로 컴파일하는데 `AppSettings`·북마크 이름이 양쪽에 겹친다. 그대로 넣을 수 없으니 필요한 부분만 가져와 이름에 `Web` 접두를 붙인다. (접근 선택은 구현자 판단 — 작성자는 결과만 지정했다.)

## 이미지 저장

### 어떤 이미지를

`<img>`만 대상이다. 패널이 페이지에 넣는 스크립트(전용 콘텐츠 월드)가 `contextmenu`와 `dragstart`에서 대상 `<img>`의 `currentSrc`·`src`·`srcset`과 페이지 주소를 앱으로 알린다. 대상이 링크(`<a>`) 안의 `<img>`여도 이미지를 찾는다. 스크립트는 사용자의 실제 동작(`event.isTrusted`)만 받는다 — 페이지가 `dispatchEvent`로 만든 가짜 우클릭·끌기로 저장될 이미지를 바꿔치기하지 못하게 한다. 끌기가 끝나면(`dragend`) 알린 이미지를 지운다.

- 주소 고르기(Swift, 단위 테스트 대상): `srcset`에 너비(`w`) 후보가 있으면 가장 큰 것, 없으면 `currentSrc`, 그다음 `src`. 상대 주소는 페이지 주소 기준으로 푼다.
- `http`·`https`·`data:`만 저장한다.

### 우클릭

`WKWebView` 하위 클래스의 `willOpenMenu`에서, 이미지 위에서 열린 메뉴면(메뉴에 `WKMenuItemIdentifierCopyImage`·`…DownloadImage`·`…OpenImageInNewWindow` 중 하나가 있으면 — 2026-11-21 로그로 확인) 맨 위에 **"'폴더이름'에 저장"** 항목을 넣는다. 저장할 실제 폴더가 없으면 **"저장할 폴더를 먼저 선택하세요"**를 비활성 항목으로 보여 준다.

- 저장할 폴더 = 지금 목록이 보여 주는 실제 폴더. 카테고리·북마크·검색·유사 이미지 결과 화면이면 "없음"이다(AI 패널의 `aiDestinationURL`과 같은 규칙).
- 폴더는 **메뉴를 누른 순간**의 것으로 고정한다. 내려받는 동안 다른 폴더로 옮겨도 바뀌지 않는다.

### 끌어다 놓기

- 목록의 빈 곳에 놓으면 지금 폴더, 목록의 폴더 타일이나 왼쪽 사이드바의 폴더 위에 놓으면 그 폴더에 저장한다.
- 놓을 자리(목록 `NSCollectionView`, 사이드바 `NSOutlineView`)는 WebKit이 이미지 드래그에 싣는 종류를 추가로 등록하고, **드래그 출발지가 웹 패널이고 패널이 방금(30초 안) 드래그 대상 이미지를 알고 있을 때만** 받는다. 등록 종류는 실제 드래그 보드에서 확인한 `[.URL, .png, .tiff]` + 파일 약속 종류다(`public.file-url`은 실리지 않는다. 드래그 시작 순간에는 파일 약속 종류만 있어 이것이 꼭 필요하다). 출발지는 웹 뷰 자신이다 — 어느 탭의 웹 뷰 또는 그 하위 뷰면 패널에서 온 것으로 본다. 저장할 주소는 드래그 보드가 아니라 스크립트가 알린 값을 쓴다(링크 안 이미지에서 링크 주소가 실리는 경우를 피한다).
- 실제 폴더가 없는 화면의 빈 곳에는 놓을 수 없다.
- 사이드바의 `validateDrop`은 지금 보드 내용을 보지 않고 폴더 행이면 무조건 받는다. 종류를 더 등록하면 받을 수 없는 드래그까지 받는 것처럼 보이므로, **파일 드래그이거나 웹 패널의 이미지 드래그일 때만** 받도록 고친다.

**함께 고치는 기존 결함**: 목록에서 파일을 폴더 타일 위에 놓아 옮기는 기능이 1.9.0(메이슨리 레이아웃 도입) 이후 동작하지 않는다. `BrowserViewController.swift`의 `itemIndexPath(at:)`가 레이아웃을 `NSCollectionViewFlowLayout`으로 가정하는데 실제 레이아웃은 `MasonryLayout`이라 항상 `nil`을 돌려준다. 웹 이미지를 폴더 타일에 놓으려면 같은 위치 판정이 필요하므로, 레이아웃과 무관한 `indexPathForItem(at:)`으로 바꾼다. 그 결과 **파일을 폴더 타일에 놓아 옮기기도 다시 동작한다**(되살아나는 동작이라 UI 테스트로 고정한다). 파일을 목록의 빈 곳에 놓는 동작은 원래 없었고 이번에도 만들지 않는다.

되살리자 옛 코드의 구멍이 함께 드러나 가드를 더했다.

- 파일 드래그는 **옮길 수 있는 폴더 타일** 위에서만 옮기기로 받는다. 이미지 타일, 폴더 자신의 타일, 자기 상위 폴더의 타일은 받지 않는다(옛 코드는 어느 타일 위든 옮기기 표시를 냈고, 폴더를 자기 타일에 놓으면 자기 안으로 옮기려 했다).
- 끌어온 항목 중 하나라도 **이미 그 폴더에 들어 있으면** 드롭 전체를 거부한다. 겹침 대화창의 "덮어쓰기"가 원본 자신을 지울 수 있었다. 같은 폴더인지는 파일 식별자로 본다(대소문자·`/private`·링크 표기가 달라도 같다).
- 옮기기 경로(`performMoveToFolder`, 사이드바 드롭도 지난다)는 원본과 대상이 같은 파일이면 대화창 없이 건너뛰고, 겹침 대화창의 덮어쓰기도 같은 파일이면 지우지 않는다. 사이드바 드롭에는 이번 작업 전부터 같은 구멍이 있었다.

### 내려받기

- `http(s)`: 고른 탭의 `webView.startDownload(using:)`로 받는다 — 같은 데이터 저장소의 쿠키가 실리고, `Referer`를 페이지 주소로 넣는다(직접 링크를 막는 사이트 대응). 저장 창 없이 정한 폴더로 간다. 내려받기는 시작한 웹 뷰에 묶이지 않는다 — 탭을 닫아 웹 뷰가 풀려도 끝까지 간다(테스트로 고정). 닫히지 않는 전용 웹 뷰를 두는 안은 버렸다: 페이지 없는 웹 뷰에서는 WebKit이 넣은 `Referer`를 출처(`http://호스트/`)로 줄였다(2026-11-22 확인). 다른 출처의 이미지는 탭의 웹 뷰로 받아도 원래 출처까지만 실린다.
- `data:`: 앱이 직접 풀어 쓴다.
- 파일 이름: 서버가 제안한 이름 → 주소의 마지막 조각 → `웹 이미지 YYYY-MM-DD HH.mm.ss`. 확장자가 없거나 이미지 확장자가 아니면 응답의 MIME으로 정한다. 이름이 겹치면 기존 `generateUniqueName` 규칙(`UniqueFileName`으로 꺼냄)으로 번호를 붙인다. 지금 내려받는 중인 이름도 겹침으로 본다(대소문자·유니코드 정규화 차이는 같은 이름). 기존 파일은 덮어쓰지 않는다.
- **이름을 정하기 전에 거른다**: HTTP 200대가 아니면 거절한다. MIME이 `image/*`이거나, 없거나 `application/octet-stream`·`binary/octet-stream`이면서 정한 이름의 확장자가 이미지 확장자일 때만 받는다. 그래서 `.jpg` 주소라도 `text/plain`·`text/html`로 오면, `application/octet-stream`이라도 이미지 확장자를 붙일 수 없으면 디스크에 닿기 전에 "이미지가 아닙니다"로 끝난다. `data:`는 `image/*`만 받는다.
- 다 받으면 앱이 여는 이미지인지 확인한다(`ImageFile(url:)?.isImage` + 실제로 읽히는지). 아니면 **방금 만든 그 파일만** 지우고 실패로 알린다.
- 결과는 패널 아래 상태 줄에 한 줄로: "저장했습니다: 이름.jpg" / "저장하지 못했습니다: 이유". 여러 개를 동시에 받을 수 있다.
- 저장 뒤 화면: **목록 화면에서 그 폴더를 보고 있을 때만** 목록을 갱신하고 새 파일을 선택한다. 뷰어로 이미지를 보고 있으면 보던 이미지를 바꾸지 않는다(상태 줄만 알리고, 목록으로 돌아가면 새 파일이 보인다). 사이드바의 폴더 개수는 갱신한다.
- `Referer`가 실제로 실리는 것을 로컬 서버 테스트에서 요청 헤더로 확인했다. 그래서 `URLSession` 대체는 만들지 않았다. 쿠키는 웹 뷰 자신의 내려받기라 같은 데이터 저장소의 것이 실릴 것으로 보지만 테스트로 확인하지는 않았다.
- 실패한 내려받기는 그 내려받기가 실제로 바이트를 쓴 경우에만 대상 파일을 지운다(같은 이름으로 먼저 끝난 다른 저장의 파일을 지우지 않게).

## 화면

```text
┌ 사이드바 ┬──────────── 웹 패널 ────────────┬───── 목록 / 뷰어 ─────┐
│          │ ‹  ›  ⟳  [검색어 또는 주소   ] ⋯ ✕ │                        │
│          │ [● 제목 하나 ✕][제목 둘 ✕][ + ]   │                        │
│  폴더    │──────────────────────────────────│   ▦ ▦ ▦ ▦              │
│  트리    │                                  │   ▦ ▦ ▦ ▦              │
│          │   웹 페이지      ── 끌어다 놓기 ─│─▶ ▦ ▦ ▦ ▦              │
│          │   (이미지 우클릭 → '폴더'에 저장) │   ▦ ▦                  │
│          │──────────────────────────────────│                        │
│          │ 저장했습니다: sunset.jpg          │                        │
└──────────┴──────────────────────────────────┴────────────────────────┘
```

- ⟳는 불러오는 동안 ✕(중지)로 바뀐다. ⋯ 메뉴: 검색엔진(Google·Bing·네이버), 검색 종류(웹·이미지).
- 주소창은 고른 탭의 페이지가 바뀌면 현재 주소를 보여 주되, 입력 중에는 덮어쓰지 않는다. 탭을 바꾸면 편집을 끝내고 그 탭의 주소를 보인다.
- 고른 탭의 웹 뷰만 패널에 붙어 있다. 뒤 탭의 웹 뷰는 떼어 두어 클릭·드래그를 받지 않는다.
- 다시 켤 때 복원 자체는 설정을 쓰지 않는다(예전 마지막 주소를 옮긴 경우만 바로 쓴다). 그 뒤 고른 탭이 불러오기를 마치면 정돈된 값(http가 아닌 주소는 빈 문자열, 범위 밖 번호는 끝 탭)으로 저장된다.
- 뷰어로 들어가도 패널은 그대로 남는다(AI 패널과 같음).

## 구성

새 파일 — `Sources/web/`

- `WebAddressResolver.swift` — 입력 해석과 검색 주소 만들기. jena-web `NavigationService`·`SearchService`에서 옮김. 검색엔진 목록은 코드에 둔다(이 앱의 빌드는 JSON 리소스를 번들에 넣지 않는다).
- `WebImageCandidate.swift` — 스크립트가 알린 값에서 저장할 주소 고르기, 파일 이름·확장자 정하기. UI 없는 순수 로직.
- `WebPageEngine.swift` — 탭 여럿을 다루는 엔진. 공유 설정(데이터 저장소·이미지 알림 스크립트·메시지 처리기), 탭 열기·고르기·닫기·복원, 새 창 → 새 탭, 탐색·대화창·내려받기 대리자, 이미지 알림 스크립트, 우클릭 메뉴. 한 페이지용 API(`currentURL`·`load`·`webView` 등)는 고른 탭에 대한 것이다. jena-web `WebKitBrowserRuntime`에서 옮기되 파비콘·사이트 설정·개인정보·앱 생명주기·링크 정책 스크립트는 뺀다.
- `WebTab.swift` — 탭 한 장(웹 뷰 + 탭별 대화창 홍수 기록·소리 멈춤·미뤄 둔 주소·저장할 주소), 탭 줄에 넘기는 값 `WebTabInfo`, 우클릭 메뉴를 꾸미는 `WebPageView`.
- `WebTabStripView.swift` — 탭 줄(항목·+ 버튼·가로 스크롤).
- `WebImageSaver.swift` — 폴더로 내려받기, 검증, 결과 알림.
- `WebPanelViewController.swift` — 머리줄·탭 줄·상태 줄·빈 화면, 탭 복원과 저장.
- `Sources/app/MainWindowController+Web.swift` — 열고 접기, AI 패널과 번갈아 열기(곁 패널 공통 처리 `setSidePanel`: 다른 패널 접기, 창 최소 폭, 처음 열 때 나눔선, 웹 버튼 상태), 저장 폴더 판단, 저장 후 목록 갱신, 드롭 연결.
- `Sources/services/UniqueFileName.swift` — 겹침 번호 규칙(아래 "구현자에게 맡기는 것"에서 꺼낸 순수 함수).

손대는 파일

- `MainWindowController.swift`(`ToolbarID.web`, 패널 상태), `+Delegates.swift`(툴바 항목), `+AI.swift`(`showAIMode`가 `setSidePanel`을 쓴다), `+FileOperations.swift`(`generateUniqueName`이 `UniqueFileName`을 쓴다 · 같은 파일 옮기기·덮어쓰기 건너뛰기), `FileService.swift`(`URL.isSameItem(as:)` — 파일 식별자 비교), `MainMenu.swift`, `BrowserViewController.swift`·`SidebarViewController.swift`(웹 이미지 드롭 · 목록 위치 판정), `AppSettings.swift`(검색엔진·검색 종류·열어 둔 탭 주소·고른 탭 번호, 예전 마지막 주소 옮기기), `Makefile`(`-framework WebKit`, 테스트 소스), `Info.plist`(http 페이지 허용: `NSAllowsArbitraryLoadsInWebContent` — 이 키가 없으면 앱 번들에서 `http://` 페이지가 App Transport Security로 막힌다, 2026-11-21 확인), `README.md`.
- 칸 번호: 웹 칸은 처음 열 때 사이드바 바로 뒤(1번)에 넣는다. 그 뒤로 목록·뷰어 칸은 2번이 되므로 `switchToMode`는 고정 번호 대신 목록·뷰어를 담은 칸(`contentSplitItem`)을 찾아 같은 자리에서 바꾼다. AI 칸은 맨 끝에 붙는다.
- 나눔선: 처음 열 때 패널과 목록·뷰어 칸 사이의 나눔선 하나를 옮긴다. 목록 왼쪽의 웹은 패널 왼쪽 끝 + 기본 폭(사이드바를 접어 두었으면 왼쪽 끝은 창 왼쪽 끝), 목록 오른쪽의 AI는 창 오른쪽 끝 − 기본 폭. 웹과 AI 사이에는 늘 목록·뷰어 칸이 있어 접힌 패널의 나눔선을 함께 옮길 일이 없다.
- 창 크기: 목록·뷰어 칸의 붙잡는 우선순위(기본 250)가 사이드바·웹·AI(260)보다 낮아, 창을 넓히고 좁히면 목록·뷰어 칸이 먼저 늘고 준다.

## 구현자에게 맡기는 것

- WebKit이 이미지 드래그에 싣는 보드 종류와 우클릭 메뉴 항목 식별자는 **먼저 로그로 실제 값을 확인**하고 정한다(문서화되지 않은 부분).
- 스크립트 알림이 메뉴가 열린 뒤 도착할 수 있다 — 주소는 항목을 누르는 시점에 읽는다.
- 주소창 단축키(⌘L 등), 머리줄 버튼의 정확한 치수·간격, 로그인 팝업 위의 닫기 표시 모양.
- `http` 페이지 허용 키가 실제로 필요한지(빌드 후 확인).
- 겹침 번호 규칙(`generateUniqueName`)은 지금 `MainWindowController`에 있어 단위 테스트가 닿지 않는다. 순수 함수로 꺼내 양쪽이 함께 쓴다.
- `make test-ui`는 번들 없는 실행 파일이라 WebKit 기본 저장소가 앱의 것이 아니다. 엔진이 데이터 저장소를 주입받게 하고(`init(dataStore:)`, 앱은 `init()` = 기본 저장소) 테스트는 비영구 저장소를 쓴다.

## 한계

- 영상(`<video>`)과 광고 등 `IFRAME`에 가린 이미지는 끌거나 우클릭으로 저장할 수 없다.
- 이미지 끌기는 페이지가 막아도 시작된다. 대신 이미지를 끌어서 넘기는 회전목마는 이 패널에서 화살표로 넘겨야 한다.
- `blob:` 이미지, CSS 배경 이미지, `<canvas>`는 저장하지 못한다(우클릭에 저장 항목이 나오지 않는다).
- `contextmenu`에서 `preventDefault()`를 부르는 사이트는 WebKit 메뉴 자체가 뜨지 않아 우클릭 저장 항목도 없다. 끌어다 놓기는 된다.
- 탭은 끌어서 순서를 바꾸거나 다른 창으로 떼어 낼 수 없다. 파비콘·방문 기록·닫은 탭 다시 열기가 없다.
- 패스키 로그인, 웹 알림, 외부 앱 링크(`mailto:` 등)는 지원하지 않는다.
- 사이트 데이터 지우기 화면이 없다. 필요하면 `~/Library/WebKit/com.jenalab.jenaimage`를 지운다.
