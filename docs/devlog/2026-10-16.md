# 2026-10-16 — 썸네일 캐시 재설계 계획 검토·반영

## 배경
`docs/superpowers/plans/2026-10-15-thumbnail-cache.md`(Task 0~9)를 착수 전에 코드 현실과 대조해 검토했다. 호출처 라인 번호·Review Focus→테스트 매핑·Task 2→7 리팩토링 예고는 모두 정확. 설계 결함 3건과 개선 5건을 계획·스펙에 반영했다.

## 변경 (문서만, 코드 변경 없음)
- **DiskStore 락 범위** — 초안은 HEIC 디코드·인코드·GC(디렉터리 전체 열거)를 모두 락 안에서 했다. 워커 8개가 디스크 계층에서 직렬화되고, `limitBytes` setter가 메인 스레드에서 GC를 동기 실행해 2GB(약 3만 파일)면 슬라이더 조작 중 UI가 1~2초 멈춘다. 락은 카운터만, GC는 utility 직렬 큐에 비동기로 걸기만 하도록 바꿨다. `clear()`는 디렉터리를 옆으로 옮겨 즉시 0으로, 실제 삭제는 GC 큐에서. 테스트 2개를 `waitUntil`로, "setter가 호출자를 막지 않음" 테스트 1개 추가.
- **같은 우선순위 LIFO → FIFO** — `didEndDisplaying` 취소 덕에 visible 큐엔 보이는 셀만 남고, 선로드도 새 선로드 때 전부 취소하므로 LIFO의 이득이 없다. 첫 화면이 아래→위로 채워지는 부작용만 있었다. 스펙 §1.2·§5.1도 갱신.
- **스켈레톤 동기화** — `beginTime = 0`은 CA가 add 시점으로 치환해 동기화되지 않는다. `1`(고정 상수)로.
- **Scheduler `cancel()` 누수** — 완료된 토큰을 취소하면 `cancelled` Set에 영원히 남았다. `running` 집합을 두고 실행 중일 때만 표시. 테스트 추가.
- **`finish` 저장 순서** — `cancelAllPending()` 뒤 도착한 결과를 버리지 않고 메모리 캐시에는 넣는다.
- **실패·미다운로드 자리표시 `hasThumbnail = true`** — 셀이 다시 보일 때마다 재요청해 스켈레톤→심볼로 깜빡이던 것 제거.
- **스파이크(Task 0)** — QuickLook 소요 시간도 측정. 2초를 넘기면 전용 워커 분리를 검토.
- **워커 수 테스트** — `peak == 2`를 `peak <= 2`로(상한 검증이 의도).
- 설정 탭(Task 8) — GC가 비동기라 1초 뒤 사용량 라벨 재갱신.

## 반영하지 않은 것
- `generate` 클로저를 CGImage 반환으로 바꿔 NSImage↔CGImage 왕복을 아끼는 것. Task 2·7의 테스트·`+App.swift`·DiskStore 연결까지 네 군데가 바뀌는 데 비해 이득(장당 변환 1회)이 작아 보류. 구현 중 프로파일에서 잡히면 그때.

# 2026-10-16 (추가) — 버그: 일부 셀이 스켈레톤으로 남고 스크롤해야 채워짐

## 증상
사용자 보고: 디스크 비우기 뒤 그리드 일부 셀이 비어 있고(어두운 네모), 스크롤을 몇 번 해야 채워진다.

## 원인
`NSCollectionView`가 `didEndDisplaying(item:forRepresentedObjectAt:)`을 **그 셀이 이미 다른 자리에 재사용된 뒤** 보내는 경우가 있다. 순서가 `prepareForReuse → configure → willDisplay(새 요청) → didEndDisplaying(옛 indexPath)`로 뒤집히면, 옛 자리의 콜백이 셀의 `thumbnailToken`(= 새 요청)을 취소한다. 셀은 다음 `willDisplay`가 올 때까지 스켈레톤으로 남는다. 비우기와는 무관하게 빠른 스크롤에서 언제든 발생. (비우기 직후 눈에 띈 건 메모리 미적중이 많아 요청이 몰렸기 때문.)

## 수정 (`BrowserViewController.swift`)
1. `didEndDisplaying`: 셀의 `representedURL`이 그 indexPath의 파일과 같을 때만 취소. 이미 재사용된 셀이면 건너뛴다.
2. 자가 치유: `prefetchAroundVisibleRect`(스크롤 멈춤 0.1초 뒤, `display` 뒤)에서 보이는 셀 중 `!hasThumbnail && thumbnailToken == nil`인 것을 다시 요청. 어떤 경로로 요청이 끊겨도 회복.

# 2026-10-16 (추가) — 버그: Finder·외부 편집으로 바뀐 파일의 그리드 썸네일이 옛 그림으로 남음

## 증상
스펙 §5.2 5번 검증 중 발견. 미리보기에서 `local.png`를 회전·저장해도 그리드 썸네일이 바뀌지 않음(삭제 반영은 정상).

## 원인
`FolderWatcher` → `refreshAfterExternalChange` → `display`는 정상 동작하지만, **메모리 캐시(`ThumbnailCache`)가 URL만 키로 쓰고 원본 mtime을 모른다.** 디스크 계층은 키에 mtime·size가 있어 괜찮지만 그 앞단인 메모리 적중이 옛 그림을 돌려줬다. 이전 코드부터 있던 결함 — 스펙 §2.2 "파일 수정 → 키가 달라짐"이 디스크 계층에만 적용돼 있었다.

## 수정
- `ThumbnailCache` — 항목에 원본 스탬프 `"<mtimeSec>|<size>"`를 함께 저장. 조회 시 현재 스탬프(새 URL 인스턴스로 읽음)와 다르면 항목을 지우고 nil. `store(_:for:stamp:)` — 스탬프가 다르면 승격 규칙과 무관하게 덮어쓴다.
- `ThumbnailProvider` — `produce` 시작 시점의 스탬프를 `Outcome.image(_, sourceStamp:)`로 넘겨 `finish`에서 그 값으로 저장(생성 중 파일이 바뀌면 다음 조회에서 미적중). `fileStamp`는 `ThumbnailCache.stamp`로 통일.
- Provider 테스트 1개 추가(mtime 변경 → 메모리 미적중 → 재생성). 총 26.

## 비용
조회마다 `stat` 1회(메인 스레드, 보이는 셀·선로드 분량만). 수십~수백 µs 단위라 체감 없음.

## 검증
- `make build` 0, `make test` 26/26. 사용자 재확인 완료 — 회전 저장 뒤 그리드 갱신 정상.
