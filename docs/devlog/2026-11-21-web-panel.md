# 2026-11-21 웹 패널

## 변경과 이유

참고 이미지를 모을 때 브라우저에서 내려받고 → Finder에서 옮기고 → JenaImage에서 확인하던 세 걸음을 한 걸음으로 줄이려고, 오른쪽 분할 칸에 한 페이지짜리 브라우저를 붙였다. 범용 브라우저를 하나 더 두려는 것이 아니다. 설계: [web-panel-design.md](../web-panel-design.md)

- **열기**: 툴바 지구본 버튼(AI 버튼 옆, 열려 있으면 켜진 상태)과 보기 → 웹 브라우저 메뉴(단축키 없음). 패널 폭 최소 360 / 기본 480 / 최대 1000. 접어도 페이지는 살아 있다.
- **패널**(`WebPanelViewController`): 머리줄 ‹ › ⟳/✕ 주소창 ⋯ ✕ · 페이지 · 상태 줄. 주소창은 jena-web 규칙 그대로(`://`가 있으면 http/https만, 공백 없고 점이 있으면 `https://`, 그 밖은 검색). ⋯ 메뉴에서 Google·Bing·네이버 × 웹·이미지 검색을 고르고 설정에 저장한다(기본 Google 이미지). 다시 켜면 마지막 주소를 한 번 연다.
- **엔진**(`WebPageEngine`): 시스템 WebKit. 기본 데이터 저장소라 로그인이 앱 재실행 뒤에도 남는다. 사용자 에이전트는 설치된 Safari 버전에 맞춘다. 카메라·마이크는 거절, 페이지 알림창은 사이트 이름을 제목으로 시트, 일반 파일은 저장 창.
- **우클릭 저장**: 이미지 위 메뉴 맨 위에 "'폴더'에 저장"(+ 구분선). 지금 목록이 실제 폴더를 보고 있지 않으면 "저장할 폴더를 먼저 선택하세요"를 비활성으로 보인다.
- **끌어다 놓기**: 웹 이미지를 목록 빈 곳(지금 폴더), 목록의 폴더 타일, 사이드바 폴더에 놓으면 그 폴더에 저장한다.
- **저장 뒤**: 상태 줄 "저장했습니다: 이름" / "저장하지 못했습니다: 사유", 사이드바 그 폴더 갱신, 그리고 목록이 바로 그 폴더를 보고 있을 때만 목록 갱신 + 새 파일 선택. 뷰어에서는 보던 이미지를 바꾸지 않는다.
- **함께 고친 것**: 1.9.0(메이슨리) 이후 죽어 있던 "파일을 폴더 타일에 놓아 옮기기"를 되살렸고, 그때 드러난 결함 둘과 리뷰에서 찾은 자기 폴더 드롭 삭제 경로를 막았다(아래 결정과 절충). 겹침 번호 규칙을 `UniqueFileName`으로 꺼내 기존 `generateUniqueName`과 저장기가 함께 쓴다.

새 파일: `Sources/web/`(`WebAddressResolver`, `WebImageCandidate`, `WebPageEngine`, `WebImageSaver`, `WebPanelViewController`), `Sources/app/MainWindowController+Web.swift`, `Sources/services/UniqueFileName.swift`, 테스트 `Tests/WebPanelLogicTests.swift`, `Tests/UI/WebPanelEngineTests.swift`, `Tests/UI/WebPanelUITests.swift`, `Tests/UI/WebTestServer.swift`. `Makefile`에 `-framework WebKit`, `Info.plist`에 `NSAllowsArbitraryLoadsInWebContent`.

## 결정과 절충

- **엔진은 jena-web에서 옮겨 다듬었다(공유하지 않음)**. 두 앱의 빌드 방식이 다르고(`swiftc` 한 번 vs CMake·Xcode), jena-web 엔진은 앱 생명주기·번들 리소스와 얽혀 있으며 `AppSettings` 같은 이름이 겹친다. 500줄을 위해 두 저장소를 묶지 않았다. 필요한 부분만 가져오고 탭·파비콘·방문 기록·사이트 설정·개인정보·링크 정책 스크립트는 뺐다. jena-web 저장소는 건드리지 않았다. 검색어의 `+`는 `%2B`로 보낸다(jena-web은 그대로 보내 "c++"가 "c  "로 검색됨 — 여기서만 고쳤다).
- **AI 패널과 한 번에 하나만 편다**. 둘 다 펴면 창 최소 폭이 1260까지 늘어난다. 공통 처리 `setRightPanel`이 다른 패널을 접고, 창 최소 폭(없음 700 / AI 940 / 웹 980)을 맞추고, 처음 열 때 나눔선을 잡고, 웹 버튼 상태를 맞춘다. 접힌 쪽의 상태는 유지한다. 나눔선은 고정 번호 `1`이 아니라 칸 위치로 구하고, 가운데 칸 오른쪽부터 그 칸 앞까지를 **모두** 같은 자리로 옮긴다 — 웹을 먼저 연 뒤 AI를 처음 열면 사이에 접힌 웹 칸이 끼어, 바로 앞 나눔선만 옮기면 AI가 최소 폭(280)으로 열렸다.
- **새 창 규칙**: `navigationType`이 `.linkActivated`(링크 클릭)면 누른 그 페이지에서 연다 — 주 페이지에서 누르면 주 페이지, 겹친 창 안에서 누르면 겹친 창(처음엔 가려진 주 페이지로 갔다가 리뷰에서 고쳤다). 그 밖(스크립트 `window.open`)은 엔진이 준 설정으로 웹 뷰를 만들어 패널 안에 닫기 줄과 함께 겹쳐 띄운다 — `window.opener`가 살아 있어 Pinterest의 Google 로그인 같은 흐름이 된다. 클릭 없는 자동 팝업은 버린다. `target=_blank` 링크로 시작하는 로그인은 opener를 잃는다(받아들임).
- **MIME 관문(설계보다 엄격)**: 이름을 정하기 전에 거른다. HTTP 200대가 아니면 거절, MIME이 `image/*`이거나 없거나 `application/octet-stream`·`binary/octet-stream`이면서 정한 이름의 확장자가 이미지 확장자일 때만 받는다. 그래서 `.jpg` 주소라도 `text/plain`·`text/html`로 오면, 확장자 없는 `application/octet-stream` 이미지도 디스크에 닿기 전에 "이미지가 아닙니다"로 끝난다. 앞의 경우는 잘못 설정된 서버의 진짜 이미지를 놓칠 수 있다 — 오류 페이지가 폴더에 남는 것보다 낫다고 봤다. `image/png`라고 오지만 본문이 HTML이면 받은 뒤 검증(`ImageFile.isImage` + 실제로 읽히는지)에서 **이번 저장이 만든 그 파일만** 지운다. `data:`는 `image/*`만 받는다.
- **내려받기는 `WKWebView.startDownload(using:)`**에 `Referer` = 페이지 주소를 넣은 요청. `Referer`가 실제로 실리는 것은 로컬 서버 테스트가 요청 헤더로 확인한다(그래서 `URLSession` 대체는 만들지 않았다). 쿠키는 웹 뷰 자신의 내려받기라 같은 데이터 저장소의 것이 실릴 것으로 보지만 **테스트로 확인하지 않았다**.
- **WebKit의 실제 값**(문서화되지 않은 부분, 저장소 밖 임시 프로그램에서 합성한 마우스 이벤트로 확인, macOS 27.2):
  - 이미지 위 우클릭 메뉴 식별자: `WKMenuItemIdentifierOpenImageInNewWindow`, `…DownloadImage`, `…CopyImage`, `…CopySubject`, `…RevealImage`, (구분선), `…ShareMenu`. 링크 안의 이미지면 앞에 `…OpenLink`, `…OpenLinkInNewWindow`, `…DownloadLinkedFile`, `…CopyLink`, 구분선. 엔진은 `CopyImage`·`DownloadImage`·`OpenImageInNewWindow` 중 하나가 있으면 이미지 메뉴로 본다. WebKit 메뉴는 `autoenablesItems = NO`라 넣는 항목의 `isEnabled`를 직접 정한다. `NSMenu.didBeginTrackingNotification`이 `willOpenMenu`보다 먼저 온다.
  - 이미지 드래그 보드: 시작 순간(`beginDraggingSession`)에는 파일 약속 종류만 있고(`com.apple.NSFilePromiseItemMetaData`, `…promised-file-name`, `…promised-file-url`, `NSPromiseContentsPboardType` 등), 0.8초쯤 뒤 `public.url`, `public.url-name`, `public.png`, `public.tiff`, `com.apple.webarchive`, `public.utf8-plain-text`, `WebURLsWithTitlesPboardType`, `com.apple.WebKit.custom-pasteboard-data`가 더해진다. `data:`·http 이미지 모두 같고 `public.file-url`은 없다. → `imageDragTypes = [.URL, .png, .tiff] + 파일 약속 종류`(설계의 대체안에서 `.fileURL`을 빼고 `.png`를 넣었다).
  - 링크 안의 이미지를 끌면 `public.url`은 이미지가 아니라 **링크 주소**다. 그래서 저장할 주소는 보드가 아니라 페이지 스크립트(전용 콘텐츠 월드, `contextmenu`·`dragstart` 캡처)가 알린 값에서 읽는다.
  - 드래그 출발지: WebKit은 `beginDraggingSession`을 웹 뷰 자신에게, `source`도 웹 뷰 자신으로 부른다. → 웹 뷰(주 페이지·겹친 창) 또는 그 하위 뷰면 패널에서 온 드래그로 본다. 그리고 dragstart 후 30초 안의 이미지 알림이 있어야 받는다.
- **되살린 폴더 타일 드롭과 다시 드러난 결함 둘**: 목록의 위치 판정이 `NSCollectionViewFlowLayout`을 가정해 메이슨리에서 늘 `nil`이었다. 웹 이미지를 폴더 타일에 놓으려고 `indexPathForItem(at:)`으로 바꾸자 파일 옮기기도 살아났는데, 옛 `draggingUpdated`의 "항목 위면 무조건 `.move`"도 함께 살아났다. ① 이미지 타일 위에서도 옮기기 표시가 나왔고 ② 폴더를 자기 타일에 놓으면 자기 안으로 옮기려 했다(테스트 프로세스가 중단됨). → 파일은 **옮길 수 있는 폴더 타일**(자기 자신·자기 상위 폴더가 아닌)에서만 받고, 그 밖은 기존처럼 기본 구현에 맡긴다. 파일을 목록 빈 곳에 놓는 동작은 원래 없었고 만들지 않았다.
- **자기 폴더 드롭 삭제 경로(리뷰에서 발견)와 두 겹 수정**: 되살린 드롭이 **이미 그 폴더에 있는 항목**(Finder에서 `/a/b/x.png`를 타일 `b`에)을 받으면, 옮기기가 같은 파일을 이름 겹침으로 보고 대화창의 "덮어쓰기"에서 원본 자신을 영구 삭제할 수 있었다(폴더면 트리째). ① 목록은 그런 항목이 하나라도 섞이면 드롭 전체를 거부한다 — 파일 식별자(`URL.isSameItem(as:)`)로 비교해 대소문자·`/private`·링크 표기 차이도 같은 폴더로 본다. ② 옮기기 경로(`performMoveToFolder`)는 원본과 대상이 같은 파일이면 대화창 없이 건너뛰고, 겹침 대화창의 덮어쓰기도 같은 파일이면 지우지 않는다. **사이드바 드롭에는 이번 작업 전부터 같은 구멍이 있었고** ②가 함께 막는다.
- **사이드바 `validateDrop`**: 전에는 보드를 보지 않고 폴더 행이면 무조건 받았다. 종류를 더 등록하면서 파일 드래그(옮기기)와 웹 이미지 드래그(복사)만 받도록 고쳤다.
- **저장기 예약 키의 `/private` 결함**: 동시에 받는 중인 이름을 예약해 겹침 번호를 매기는데, 키가 `standardizedFileURL`을 썼다. 이 값은 파일이 **있을 때만** `/private`를 떼어 낸다(`/private/var/…/x.png`: 쓰기 전 그대로, 쓴 뒤 `/var/…`). 그래서 `/private` 아래 폴더에 저장하면 예약할 때와 풀 때 키가 달라 예약이 영영 남았고, 그 파일을 지운 뒤 다시 받아도 `이름 2.png`가 됐다. 늘 있는 부모 폴더 쪽만 표준화하도록 고쳤다. 예약 키는 대소문자·유니코드 정규화도 무시한다(기본 APFS에서 대소문자만 다른 두 이름을 동시에 받으면, 실패한 쪽 정리가 이긴 쪽 파일을 지우던 문제를 리뷰에서 찾아 고쳤다). 실패한 내려받기는 실제로 바이트를 쓴 경우에만 대상 파일을 지운다.
- **폴더는 고른 순간에 정해진다**: 우클릭 항목을 누른 순간·놓은 순간의 폴더가 저장 작업에 실린다. 내려받는 동안 폴더를 옮기거나 패널을 접어도 처음 폴더로 간다. 실제 폴더가 없는 화면(카테고리·북마크·검색·유사 이미지)에서는 저장하지 않는다(AI 패널의 `aiDestinationURL`과 같은 규칙).
- **`http://` 페이지 허용 키는 실제로 필요하다**: 앱의 `Info.plist`를 그대로 쓴 임시 번들에서는 `http://example.com`이 열렸고, 이 키만 지운 번들에서는 "The resource could not be loaded because the App Transport Security policy requires the use of a secure connection."으로 막혔다. 번들 없는 실행 파일(`make test-ui`)에서는 키와 상관없이 열린다.

### 실제 사이트(프로그램으로 확인)

저장소 밖 임시 프로그램이 `make test-ui`와 같은 방식으로 앱 소스를 컴파일해 `WebPageEngine(dataStore: .nonPersistent())`와 `WebImageSaver`를 실제 인터넷에 붙였다. 검색어는 "노을"만 썼고 요청은 몇 번으로 끝냈다. 임시 코드는 저장소에 남기지 않았다.

- **Google 이미지 검색**: `resolve("노을", provider: .google, mode: .images)` = `https://www.google.com/search?udm=2&q=%EB%85%B8%EC%9D%84`. 실패 알림 없이 끝까지 불러왔고 제목 "노을 - Google 검색", `<img>` 250개(화면에 보이고 읽힌 60pt 이상 83개).
- **우클릭 → 저장(합성 `contextmenu`)**: 실제 결과 이미지에 `contextmenu`를 보내자 페이지 스크립트가 이미지를 알렸다. 화면의 결과 썸네일은 `data:image/jpeg` 주소였고, 저장기가 `웹 이미지 2026-11-21 23.27.53.jpg`(9,668바이트, 183×275)로 썼으며 `ImageFile.isImage` 참·`NSImage`로 읽힘. 아래로 스크롤해 `https://encrypted-tbn0.gstatic.com/images?q=…` 이미지도 저장해 봤다 — `startDownload` 경로로 `images.jpeg`(30,892바이트, 680×451), 역시 이미지로 확인.
- **실제 합성 우클릭 메뉴(Google 결과 위)**: 맨 위 "'폴더'에 저장", 구분선, 그다음 WebKit의 링크 항목들과 이미지 항목들. 식별자는 위 "WebKit의 실제 값"과 같았다(결과 썸네일은 링크 안의 이미지).
- **Pinterest**: `https://www.pinterest.com` → `https://kr.pinterest.com/`, 제목 "Pinterest - 핀터레스트", 실패 알림 없음. 로그인 팝업은 손이 필요해 보지 못했다.
- **`http://` 페이지**: `http://example.com` — 번들 없는 실행 파일: 열림. 앱 `Info.plist`를 그대로 쓴 임시 번들(번들 ID만 바꿈): 열림. 키를 지운 번들: ATS로 막힘(위 결정과 절충). 실제 `.build/JenaImage.app` 안에서 웹 패널을 띄워 확인하지는 못했다 — 같은 `Info.plist`라 같게 동작할 것으로 본다.
- **앱 실행**: `make run`으로 한 번 띄워 5초 넘게 떠 있는 것을 보고 종료했다. 충돌 보고서 없음.
- 덧붙여 본 것: Google 썸네일은 서버가 `images.jpeg`라는 이름을 주므로 여러 장을 모으면 `images 2.jpeg`, `images 3.jpeg`…가 된다(동작은 맞다).

### 작성자 확인 필요

손으로만 확인할 수 있어 통과로 적지 않은 항목이다. `make run` 뒤 몇 분이면 된다.

1. **열고 접기·AI와 번갈아** — 툴바 지구본을 눌러 열고 다시 눌러 접는다. 패널이 사이드바와 목록 사이에 기본 폭으로 열리는지. AI 버튼을 누르면 웹이 접히고 AI가 오른쪽 끝에 기본 폭으로 열리는지.
2. **우클릭 저장(실제 사이트)** — 목록에서 폴더 하나를 연 채 패널에서 Google 이미지 검색 → 결과 이미지 우클릭 → "'폴더'에 저장" → 목록에 새 파일이 나타나고 선택되는지. 카테고리 화면에서는 항목이 비활성 "저장할 폴더를 먼저 선택하세요"인지.
3. **끌어다 놓기 세 곳** — 웹 이미지를 ① 목록 빈 곳 ② 목록의 폴더 타일(강조 표시) ③ 왼쪽 사이드바 폴더에 놓아 각 폴더에 저장되는지. 놓는 자리에서 복사(+) 커서가 뜨는지(WebKit이 드래그 동작에 복사를 허용하는지 미확인).
4. **Pinterest → Google 로그인** — pinterest.com에서 "Google로 계속하기"를 눌러 로그인 창이 패널 안에 닫기 줄과 함께 겹쳐 뜨고, 로그인 뒤 저절로 닫히며 원래 페이지가 로그인 상태가 되는지.
5. **재실행 후 유지** — 로그인한 채 앱을 종료했다 다시 켜고 웹 패널을 열면 마지막 주소가 다시 열리고 로그인이 남아 있는지.
6. **영상(mp4)** — Pinterest 동영상 핀 등에서 재생·스크롤이 되는지.
7. **쿠키 동승** — 로그인해야 보이는 이미지를 우클릭 저장해 받아지는지(테스트로 확인하지 않은 부분).
8. **기존 동작** — AI 패널, 뷰어, 목록 안·사이드바로 파일 끌어다 옮기기, Finder에서 폴더 타일로 파일 옮기기가 전과 같은지. 이미 그 폴더에 있는 파일을 그 폴더 타일에 놓으면 아무 일도 없는지.
9. **나눔선으로 접고 펴기** — 웹 패널과 목록 사이의 나눔선(웹 패널 오른쪽)을 끝까지 끌어 접었다가 다시 끌어 편다. 툴바 버튼이 꺼졌다 켜지는지, 접은 뒤 창을 좁혔다가 다시 펴면 패널이 창 밖으로 잘리지 않는지(나눔선으로 펼 때는 창을 넓혀 주지 않는다 — 재검토에서 나온 남은 점).
10. **저장 중 종료** — 큰 이미지를 저장하자마자 창을 닫아 앱을 끝낸 뒤, 그 폴더에 잘린 파일이 남았는지 본다. 창을 닫을 때 진행 중 저장을 취소하고 지우지만, 지우기가 WebKit의 응답을 기다리는 사이 앱이 먼저 끝날 수 있다(재검토에서 나온 남은 점). 남는다면 종료를 잠깐 미루는(`applicationShouldTerminate` → `.terminateLater`) 보완이 필요하다.
11. **접어 둔 페이지** — 영상이 나오는 페이지를 띄운 채 패널을 접으면 소리가 멈추는지, 알림창을 띄우는 페이지가 접힌 동안 이미지 창 위에 창을 띄우지 않는지.

## 최종 검토에서 고친 것

전체 변경을 한 번에 본 마지막 리뷰의 지적(F1–F9)을 한 번에 고쳤다.

- **F1 접힌 패널의 시트**: 접어도 페이지가 살아 있어, 보이지 않는 페이지가 주 창에 alert·저장 창 시트를 띄워 이미지 화면을 막을 수 있었다(마지막 주소로 저장돼 다시 켜도 되풀이). 엔진에 보임 표시(`isPresented`, 창 컨트롤러가 맞춤, 기본은 보이지 않음)를 두고, 보이지 않으면 alert 통과·confirm false·prompt null·파일 선택 없음·일반 받기 취소(알림 한 줄)로 답한다. 보일 때도 한 페이지가 10초 안에 알림창을 셋 넘게 띄우면 다음 페이지까지 자동으로 답한다. 이미지 저장은 그대로 끝까지 간다.
- **F2 이미지 알림**: 캡처 리스너를 `document`에서 `window`로 옮겨, 페이지가 window 캡처 단계에서 전파를 끊어도 먼저 듣는다. 놓기가 끝난 드래그는 지워서(`clearDraggedImage`) 새 dragstart 없는 다음 드래그가 같은 이미지를 다시 저장하지 않는다(끄는 동안 엿보기는 그대로).
- **F3 소리**: 접으면 주 페이지와 겹친 창의 소리·영상을 멈추고 펼치면 되살린다. WebKit은 멈춤 요청을 겹쳐 세어, 되살리기 한 번이 여러 번의 멈춤을 풀지 못했다(시험으로 확인). 그래서 웹 뷰마다 상태를 기억해 바뀔 때만 부른다. 페이지가 없는 웹 뷰는 첫 페이지가 들어설 때 맞춘다.
- **F4 창 넓히기**: 최소 폭까지 넓힌 창이 화면 오른쪽 밖으로 나가지 않게 왼쪽으로 당기고, 화면이 더 좁으면 화면 폭에 맞춘다. AI 패널도 같은 길을 쓴다.
- **F5 나눔선으로 접기**: 버튼·창 최소 폭·보임 표시가 `setRightPanel` 안에서만 맞춰졌다. 오른쪽 패널 항목의 `isCollapsed`를 관찰하고 나눔선 크기 변화에서도 같은 맞춤(`syncRightPanelState`)을 부른다. 최소 폭은 펼친 패널의 값(웹 980·AI 940, 없으면 700)이라 "하나만 펴진다"는 가정이 없어졌다.
- **F6 종료 중 저장**: 마지막 창을 닫으면 앱이 끝나는데, 쓰던 저장은 결과 콜백 없이 조각 파일로 남을 수 있었다. 창이 닫힐 때 `WebImageSaver.cancelAll()`이 진행 중 저장을 취소하고, 바이트를 받은 대상(이번 저장이 만든 파일)만 지운다. WebKit은 취소한 받기의 조각을 이어받기용으로 남기므로 취소 직후와 취소가 끝난 뒤 두 번 지운다.
- **F7 격리 속성**: 저장소 밖 임시 프로그램으로 일반 받기와 같은 `WKDownload` 경로를 시험했다. 번들 없는 실행 파일과 앱 `Info.plist`를 쓴 임시 번들 모두 받은 파일에 `com.apple.quarantine: 0083;…;;`이 붙었다(WebKit이 붙인다). 그래서 코드는 바꾸지 않았다. 같은 경로를 쓰는 이미지 저장에도 붙는다 — 앱 안에서 여는 데는 문제가 없어 그대로 둔다.
- **F8 문서**: `contextmenu`를 막는 사이트에서는 우클릭 저장 항목이 없다는 한계를 설계 문서에 적었다.
- **F9 테스트 위생**: 웹 패널 UI 스위트가 끝나면 공용 창을 되돌린다(패널 접힘, 최소 폭 700, 보던 폴더를 정상 경로로 다시 열기, 마지막 주소 복원). "두 번째 호출은 무시" 검사는 열 수 있는 다른 주소로 바꾼 뒤 1.5초 기다려 보게 했다(가드를 지우면 실패하는 것을 확인).

## 남은 것

리뷰에서 나왔지만 이번에 고치지 않은 작은 항목이다.

- **이름·주소 처리**: 제어 문자나 255바이트를 넘는 파일 이름을 따로 거르지 않는다. `srcset`의 설명자가 둘인 후보나 `0w`를 관대하게 받는다. `://`와 공백이 함께 든 입력은 검색이 아니라 오류가 된다(jena-web과 같음). 이 셋은 MIME 관문과 받은 뒤 검증이 있어 이미지 아닌 파일이 남지는 않는다.
- **팝업·스크립트**: 겹친 창이 또 창을 열면 앞의 창을 닫아 연쇄 로그인(OAuth)에서 opener가 끊길 수 있다.
- **패널 화면**: 주소창에 입력하다 Return 없이 페이지를 누르면 입력한 글자가 다음 탐색까지 남는다. 오류 페이지(4xx/5xx)나 실패한 주소가 마지막 주소로 저장될 수 있다.
- **저장 뒤 화면**: 연달아 저장하면 마지막 파일만 선택되고, 저장마다 폴더 전체를 다시 읽는다. 지금 폴더를 `/var/…`처럼 링크 거친 경로로 열었으면 저장은 되지만 새 파일이 선택되지 않을 수 있다.
- **드롭**: 드래그 출발지가 허용한 동작(`draggingSourceOperationMask`)을 보지 않고 복사·옮기기를 돌려준다. 같은 이름의 하드 링크는 같은 항목으로 보고 조용히 건너뛴다. 폴더 심볼릭 링크를 거친 드롭은 받은 뒤 아무 일도 하지 않는다(손실 없음). 대소문자를 구분하는 볼륨에서는 자기·상위 폴더 판정이 조금 더 거부할 수 있다(잘못 옮기지는 않는다). 복사·잘라 붙이기에는 같은 폴더 건너뛰기가 없다(이전과 같은 동작).
- **테스트 빈틈**: 상태 줄 6초 지움, 메뉴로 열었을 때 툴바 버튼 상태, 예약 키 단위 테스트, 실패 시 삭제 가드(실제로 바이트를 썼을 때만)를 직접 고정하는 테스트가 없다. 대소문자 겹침 테스트는 WebKit 타이밍에 기대고(거짓 실패는 없다), "대소문자만 다른 경로" 드롭 테스트는 실제로 폴더 대소문자를 시험하지 않는다. UI 테스트 일부가 앞 테스트가 남긴 파일에 기댄다. 가짜 드래그(`FakeDrag`)는 AppKit의 등록 종류 거름을 건너뛰므로 실제 손 드래그는 위 "작성자 확인 필요"로 남는다. 복사 경로 가드·사이드바 경로는 모달 뒤라 회귀가 '멈춤'으로만 드러난다.

## 2026-11-22 — 웹 패널을 사이드바와 목록 사이로

작성자가 써 보니 오른쪽 자리가 불편했다. 웹 패널을 사이드바와 목록·뷰어 사이로 옮겼다. 칸 배치는 [사이드바 | 웹 | 목록·뷰어 | AI]이고 AI 패널은 그대로 오른쪽 끝이다. 그 밖의 동작(한 번에 하나만 펴기, 창 최소 폭, 버튼·메뉴·닫기, 저장과 끌어다 놓기)은 바꾸지 않았다. 위의 '오른쪽'·`setRightPanel` 서술은 그때의 기록이다.

- **칸 번호**: 웹 칸은 처음 열 때 사이드바 바로 뒤(1번)에 넣는다(`insertSplitViewItem(_:at: 1)`). 그 뒤로 목록·뷰어 칸은 2번이 되므로 `switchToMode`는 고정 번호 `1` 대신 목록·뷰어를 담은 칸(`contentSplitItem`)을 찾아 같은 자리에서 바꾼다. 웹 칸이 아직 없으면 1번 그대로다. 사이드바 토글은 계속 `splitViewItems.first`다.
- **나눔선**: 공통 처리를 `setSidePanel`로 이름을 바꿨다(관련 상태도 `sidePanel…`). 처음 열 때 패널과 목록·뷰어 칸 사이의 나눔선 하나만 옮긴다 — 목록 왼쪽의 웹은 패널 왼쪽 끝 + 480(사이드바를 접어 두었으면 창 왼쪽 끝부터), 목록 오른쪽의 AI는 전처럼 창 오른쪽 끝 − 300. 웹과 AI 사이에는 늘 목록·뷰어 칸이 있어, 전에 있던 "접힌 칸의 나눔선까지 함께 옮기기"는 필요 없어졌다.
- **창 크기**: 목록·뷰어 칸의 붙잡는 우선순위(기본 250)가 사이드바·웹·AI(260)보다 낮아 창을 넓히고 좁히면 목록·뷰어 칸이 늘고 준다. 테스트로 확인했다.
- **테스트**: 옛 자리를 고정하던 검사("맨 오른쪽", 가운데 칸 1번)를 새 자리(웹 1번, 목록·뷰어 2번, AI 맨 끝)로 바꿨다. 웹 먼저·AI 먼저 두 순서의 처음 열기(칸 순서, 웹 480·AI 300, 뷰어 전환), 사이드바를 접은 채 처음 열기와 사이드바 토글, 다시 열 때 남긴 폭, 창 크기 변화를 목록이 받는지를 더했다. `AIImageUITests`는 그대로 통과한다(웹 칸이 없을 때 목록 1번).
- **결과**: 빌드 성공(경고 0), `make test` 129개, `make test-ui` 134개 통과(새 테스트 3개 포함, 두 번 실행해 둘 다 통과). 손으로는 위 "작성자 확인 필요" 1·9번을 새 자리에서 다시 본다.

## 2026-11-22 — Google Drive 폴더에서 삭제가 안 되던 문제

작성자가 웹 패널을 쓰다 알려 준 문제다. 웹 패널과는 무관하게 전부터 있던 결함이다(삭제 코드는 이번 작업에서 바뀌지 않았다).

- **증상**: Google Drive 폴더(`~/Library/CloudStorage/GoogleDrive-…`)에서 목록의 우클릭 → 삭제와 백스페이스가 파일을 지우지 못하고 "일부 파일을 삭제할 수 없습니다"만 떴다.
- **원인(확인)**: macOS는 앱이 파일 제공자 폴더의 파일을 그 폴더의 휴지통(`<도메인>/.Trash`)으로 옮기려 할 때 **전체 디스크 접근 권한**을 확인한다. 앱에 그 권한이 없으면 `FileManager.trashItem`이 `NSCocoaErrorDomain 513`으로 거절된다. 권한 판정 기록에 `kTCCServiceSystemPolicyAllFiles`, 결과 0이 남는다. 앱이 직접 만든 파일만 예외로 통과한다.
- **어떻게 가렸나**: 임시 진단 모드를 넣어 앱의 신분으로 화면 없이 실행해, 시험 파일로 조건을 하나씩 바꿨다.

  | 조건 | 휴지통 이동 |
  |---|---|
  | 앱이 만든 파일 · 내 드라이브 / 공유 드라이브 | 됨 |
  | 앱이 만든 파일 + 격리 표시 | 됨 |
  | 다른 프로세스가 만든 파일 · 내 드라이브(격리 표시·동기화 여부 무관) | **거절(513)** |
  | 다른 프로세스가 만든 파일 · 로컬 폴더 | 됨 |
  | 거절된 파일의 같은 폴더 안 이름 바꾸기 / `removeItem` | 됨 |

  `NSWorkspace.recycle`도 같은 파일에서 똑같이 거절됐다("You do not have permission to move the file … to the trash."). 위치(공유 드라이브)·격리 표시·동기화 상태는 원인이 아니었다. Finder는 같은 파일을 휴지통에 넣는다(Finder에는 권한이 있다).
- **조사에서 헛짚은 것**(다음 사람을 위해): ① zsh에서 `log`는 셸 내장 함수라 `log show`가 조용히 아무것도 안 했다 — `/usr/bin/log`로 써야 한다. ② 테스트 틀에서 `collectionView.keyDown`으로 보낸 백스페이스는 메뉴 단축키를 거치지 않아 삭제에 닿지 않는다(실제 앱의 백스페이스는 메뉴의 삭제 항목이 받는다). ③ 처음엔 `NSWorkspace.recycle`로 다시 시도하면 될 거라 보고 넣었으나 같은 권한 판정에 막혀 뺐다. ④ `NSLog` 내용은 시스템 기록에 `<private>`로 가려져 읽을 수 없다.
- **고친 것**(작성자 결정: 바로 삭제를 물어보기)
  - 휴지통으로 옮길 수 없으면(권한 없음 513 · 휴지통 없는 볼륨 3328) Finder처럼 한 번 더 묻는다: "'이름'을(를) 휴지통에 넣을 수 없습니다. 바로 삭제할까요?" **취소가 기본 버튼**이고(Enter로 지워지지 않는다), 바로 삭제는 파괴적 동작 버튼, 세 번째는 "권한 설정 열기…"(전체 디스크 접근 권한 화면)다.
  - 바로 삭제는 이 Mac의 휴지통에 들어가지 않는다. Google Drive는 지운 파일을 웹의 Drive 휴지통에 보관하지만, 앱은 그것을 보장하지 않으므로 창에 "클라우드 폴더라면 그 서비스의 휴지통에 남을 수 있습니다"라고만 적는다.
  - 여럿을 지울 때 휴지통으로 가는 것은 그대로 보내고, 못 가는 것만 모아 한 번 묻는다. 그만두면 그 항목은 그대로 두고 오류로 알리지 않는다.
  - **폴더는 바로 삭제하지 않는다.** 안의 것까지 되돌릴 수 없이 지워지고 도중에 실패하면 일부만 사라지기 때문이다. 폴더는 "Finder에서 지우거나 전체 디스크 접근 권한을 주세요"라고 알린다(검토에서 나온 지적).
  - 안내 문구는 까닭에 따라 다르다. 권한 없음(513)이면 클라우드 폴더·전체 디스크 접근 권한을 말하고 "권한 설정 열기…"를 붙인다. 휴지통 없는 볼륨(3328)이면 "이 볼륨에는 휴지통이 없습니다"만 말하고 설정 버튼을 붙이지 않는다. 일부가 이미 휴지통으로 갔으면 그 개수를 먼저 알린다.
  - 권한 문제가 아닌 실패(파일 없음 등)에는 바로 삭제를 권하지 않고, 어떤 파일이 왜 안 지워졌는지 보여 준다(앞의 셋 + 나머지 개수).
  - 썸네일·북마크·카테고리 정리와 "보던 폴더가 지워지면 부모로 이동"은 실제로 지워진 항목에만 한다.
  - 뷰어는 보던 이미지가 **실제로 지워졌을 때만** 다음 이미지로 넘어간다. 전에는 확인창에서 취소해도, 삭제에 실패해도, 사이드바에서 다른 폴더를 지워도 보던 이미지를 뺐다.
  - 앱에 전체 디스크 접근 권한을 주면 휴지통 이동이 그대로 되고 이 질문은 뜨지 않는다. 다만 이 앱은 ad-hoc 서명이라 다시 빌드하면 권한을 다시 줘야 한다.
- **검증**: `Tests/UI/DeleteFallbackTests.swift` 12개(확인하면 바로 삭제 · 그만두면 그대로이고 오류 없음 · 휴지통이 되면 묻지 않음 · 섞이면 못 가는 것만 물음 · 바로 삭제도 실패하면 이유를 알림 · 다른 오류에는 권하지 않음 · 폴더는 바로 삭제하지 않음 · 그만둔 항목의 북마크 유지 · 확인 창의 버튼 순서와 기본 버튼 · 오류 종류 가르기 · 문구 · 실제 파일 서비스). 테스트는 휴지통 이동과 확인 창을 바꿔 끼워 실제 휴지통과 모달을 건드리지 않는다. 진단 코드는 원인을 확인한 뒤 지웠다. 사이드바에서 지울 때도 뷰어가 보던 이미지를 맞게 뺀다.
- **작성자 확인 필요**: ① Google Drive 폴더에서 우클릭 삭제·백스페이스 → 질문 창 → 바로 삭제로 실제로 지워지는지, 취소·Enter로는 안 지워지는지 ② 뷰어에서도 같은지 ③ "권한 설정 열기…"가 전체 디스크 접근 권한 화면을 여는지 ④ 두 창 모두에서 Esc가 취소로 듣는지(앱에 지역화 묶음이 없어 안 들을 수 있다) ⑤ 바로 삭제한 파일이 웹의 Drive 휴지통에 실제로 남는지.
- **결과**: 빌드 성공(경고 0), `make test` 129개, `make test-ui` 146개 통과.

## 2026-11-22 — 어떤 사이트에서는 끌어다 놓기가 안 되던 문제

작성자가 civitai·Pinterest에서 "우클릭 저장은 되는데 끌기가 안 되는 이미지가 있다"고 알려 줬다.

- **확인한 원인**(civitai 실제 화면을 열어 이미지 구조를 읽음)
  - 모델 화면의 넘겨 보는 큰 이미지와 작은 미리보기는 페이지가 `dragstart`를 취소한다(회전목마가 끌어서 넘기는 동작을 쓰려고). 끌기 자체가 시작되지 않으니 놓을 것이 없다. 목록 화면의 이미지는 막지 않아 잘 됐다.
  - 일부 이미지는 다른 요소(덮개 `DIV`)에 가려 있다. 끌기·우클릭의 대상이 덮개라 스크립트가 이미지를 찾지 못했다.
  - 광고 `IFRAME`에 가린 이미지는 페이지 밖 문서라 손댈 수 없다.
- **고친 것**(이미지 알림 스크립트)
  - 이미지 끌기는 페이지 처리기에 닿기 전에 전파를 끊어 **페이지가 취소하지 못하게** 한다. 이미지가 아닌 것(글 등)을 끌 때는 페이지에 그대로 맡긴다. 대가: 그 이미지를 마우스로 끌어 회전목마를 넘기는 동작은 이 패널에서 되지 않는다(화살표로 넘긴다).
  - `draggable=false`·`-webkit-user-drag: none`인 이미지와 덮개에 가린 이미지는 **누르고 있는 동안만** 끌 수 있게 바꿨다가 떼면 되돌린다.
  - 이미지를 찾는 순서에 "포인터 아래에 깔린 요소들 중 `<img>`"를 더했다. 좌표가 정말 그 대상을 가리킬 때만 본다. 덮개에 가린 이미지의 우클릭 저장도 함께 된다.
  - 패널에서 끌어왔지만 이미지를 찾지 못한 드래그가 목록·사이드바에 들어오면 패널 상태 줄에 "끌어온 항목에서 저장할 이미지를 찾지 못했습니다."를 보인다(전에는 아무 반응이 없었다).
- **검증**: 엔진 테스트 3개 추가(페이지가 막아도 끌기 시작 · 끌 수 없는 이미지를 누르는 동안만 바꿈 · 덮개에 가린 이미지). 실제 civitai 모델 화면에 같은 스크립트를 넣어 비교: 막히던 489×715 이미지가 "취소됨 → 취소 안 됨", 덮개에 가린 이미지도 알림에 실렸다. **실제 손 끌기는 확인하지 못했다**(합성 이벤트로 본 것).
- **여전히 안 되는 것**: 영상(`<video>` — 움직이는 미리보기 대부분), 광고 등 `IFRAME`에 가린 이미지, CSS 배경·`<canvas>`·`blob:` 이미지. Pinterest는 로그인 화면이라 구조를 직접 확인하지 못했다.
- **결과**: 빌드 성공(경고 0), `make test` 129개, `make test-ui` 149개 통과.

## 2026-11-22 — 탭

작성자가 써 보고 "탭도 추가해줘"라고 했다. 처음 설계의 "한 페이지"를 탭 여럿으로 넓히고, 스크립트 창을 패널 위에 겹쳐 띄우던 팝업을 새 탭으로 바꿨다. 겹침 팝업(닫기 줄 "새 창", `hasPopup`, `closePopup()`)과 "새 창 링크는 누른 페이지에서 연다" 규칙은 지웠다.

- **화면**: 머리줄 바로 아래 탭 줄(`WebTabStripView`). 항목은 제목(없으면 주소의 호스트, 그것도 없으면 "새 탭", 길면 말줄임) + ✕(접근성 "탭 닫기: 제목"), 고른 탭은 옅은 바탕과 굵은 글씨. 폭 90~180, 넘치면 옆으로 스크롤하고 새로 연 탭·고른 탭이 보이게 한다. 끝에 +(툴팁·접근성 "새 탭") — 빈 탭을 열어 고르고 주소창에 포커스. 보기 → 새 탭(단축키 없음, 패널이 펼쳐져 있을 때만 켜짐). 파비콘은 없다.
- **엔진**(`WebPageEngine` + `WebTab`): 공유 설정·데이터 저장소·이미지 알림 스크립트·메시지 처리기는 엔진 하나가, 웹 뷰와 탭별 상태(대화창 홍수 기록·소리 멈춤·미뤄 둔 주소·저장할 주소)는 탭이 갖는다. 탭이 닫히면 관찰·대리자를 끊고 탭 객체와 함께 상태가 사라진다. 한 페이지용 API(`currentURL`·`isLoading`·`canGoBack`·`load`·`goBack`·`reloadOrStop`·`webView`)는 고른 탭에 대한 것으로 남겨 호출부를 거의 바꾸지 않았다. 탭 API: `tabs: [WebTabInfo]`, `selectedTabID`, `openTab(url:select:)`, `selectTab(_:)`, `closeTab(_:)`, `restoreTabs(addresses:selectedIndex:)`, `onTabsChange`, `webView(forTab:)`, `tabAddresses`, `selectedTabIndex`.
- **보이는 것은 고른 탭 하나**: 패널(`containerView`)에는 고른 탭의 웹 뷰만 붙어 있다. 뒤 탭의 웹 뷰는 떼어 두어 클릭·드래그를 받지 않는다. 대화창·파일 선택·저장 창은 펼친 패널의 고른 탭만 띄우고, 뒤 탭과 접힌 패널의 탭은 전의 "보이지 않을 때" 규칙(alert 통과·confirm false·prompt null·선택 없음·일반 받기 거절+알림)을 따른다. 홍수 계수는 탭마다 따로다. 소리·영상도 고른 탭이면서 패널이 펼쳐져 있을 때만 난다(웹 뷰마다 적용 상태를 기억하는 기존 방식 그대로).
- **새 창 → 새 탭**: `createWebViewWith`의 모든 새 창을 WebKit이 준 설정으로 만든 새 탭으로 연다(`window.opener`·POST 본문·로그인 맥락 유지, jena-web과 같은 방식). ⌘를 누른 채 연 것은 뒤에서, 그 밖은 앞에서. 새 탭은 연 탭 바로 뒤(그 탭이 먼저 연 탭들 뒤)에 놓는다. `window.close()`면 그 탭을 닫고 연 탭으로 돌아간다. http/https가 아닌 주소의 새 창은 전처럼 거절하고 알린다. 예전에 받아들였던 "`target=_blank`로 시작하는 로그인은 opener를 잃는다"는 이제 없다.
- **이미지 알림·저장·끌기**: `isDragSource`는 모든 탭의 웹 뷰를 본다. 이미지 알림은 처음엔 어느 탭에서 오든 받았으나 리뷰 수정에서 고른 탭의 것만 받도록 바꿨다(아래).
- **다시 켰을 때**: `webTabAddresses`(빈 탭은 빈 문자열)와 `webSelectedTabIndex`로 복원하고, 고른 탭만 바로 불러온다(나머지는 처음 고를 때, 그 전에도 제목은 호스트). 예전 `webLastAddress`만 있으면 탭 하나로 옮기고 지운다(`AppSettings.takeLegacyWebLastAddress()` — 읽어 옮기는 코드만 남김). 탭이 열리고·닫히고·고른 탭이 바뀌고·주소가 바뀔 때 저장한다(주소는 불러오기가 끝난 http/https만 — 오류 페이지 주소도 그대로, 기존 동작).

### 결정과 절충

- **이미지 저장은 전용 웹 뷰가 아니라 고른 탭의 웹 뷰로 시작한다**. 요구는 "저장이 특정 탭에 묶이지 않게(닫히지 않는 전용 웹 뷰, 또는 근거를 적은 다른 방법)"였다. 전용 웹 뷰를 먼저 만들어 봤더니, 페이지가 없는 웹 뷰에서는 WebKit이 넣어 준 `Referer`를 출처로 줄였다(`http://127.0.0.1:포트/page.html` → `http://127.0.0.1:포트/`) — 기존 Referer 테스트가 실패했다. 전용 웹 뷰에 `<meta name=referrer content=unsafe-url>` 문서를 띄워 보는 시험도 같은 결과였다(다만 그 문서가 첫 저장 전에 다 불렸는지는 확인하지 않았다 — 불러오기를 기다려야 하는 길이라 더 파지 않았다). 반면 탭의 웹 뷰로 시작한 내려받기는 **그 탭을 닫아 웹 뷰가 풀린 뒤에도(약한 참조가 nil, 그때 결과는 아직 0건) 끝까지 가서 파일이 생겼다**. WKDownload는 네트워크 프로세스의 것이라 시작한 웹 뷰의 수명과 무관하다(Safari도 탭을 닫아도 받기가 계속된다). 그래서 저장기는 시작할 때 고른 탭의 웹 뷰를 빌리기만 하고 그 뒤로 묶이지 않는다. 덧붙여 확인한 것: 다른 출처(`localhost` ↔ `127.0.0.1`)의 이미지는 탭의 웹 뷰로 받아도 `Referer`가 출처까지만 실린다 — 이번 변경 전부터의 동작이다.
- **테스트 실행기와 자동 해제 풀**: 테스트 실행기는 앱의 이벤트 고리처럼 자동 해제 풀을 비우지 않는다. 풀 밖에서 만든 탭의 웹 뷰는 닫아도 끝까지 풀리지 않아(30초 기다려도) 처음엔 내려받기가 웹 뷰를 붙잡는 줄 알았다. 탭을 만들고 닫는 구간을 `autoreleasepool`로 감싸니 바로 풀렸다. "웹 뷰가 풀린다" 검사 둘은 그렇게 쓴다.
- **고른 탭을 닫으면**: 요구는 "그 자리의 다음 탭(없으면 앞 탭)". 여기에 하나를 더했다 — 새 창으로 열린 탭이고 연 탭이 아직 있으면 연 탭으로 돌아간다(`window.close()` 뒤 "연 탭으로 돌아온다"는 요구를 뒤에 다른 탭이 있어도 지키려고).
- **뒤 탭의 일반 내려받기 알림**: 접힌 패널의 문구("패널이 접혀 있어 내려받기를 취소했습니다.")가 뒤 탭에는 맞지 않아, 패널이 펼쳐져 있는데 뒤 탭(또는 닫힌 탭)에서 온 받기면 "뒤에 있는 탭의 내려받기를 취소했습니다."를 알린다(요구서에 없던 문구).
- **탭 줄 모양**: jena-web의 탭 줄(폭 180 고정, 파비콘)을 참고하되 패널이 좁아(360~1000) 폭을 90~180 사이로 나누고 파비콘을 뺐다. 버튼은 패널 머리줄과 같은 테두리 없는 보조 색 버튼.
- **⌘클릭**: `target=_blank` 링크의 ⌘클릭은 뒤 탭으로 연다. 보통 링크의 ⌘클릭·가운데 클릭은 리뷰 수정에서 뒤 탭으로 열게 했다(아래).

### 작성자 확인 필요

1. **Pinterest → Google 로그인** — 로그인 창이 새 탭으로 열리고, 로그인 뒤 그 탭이 저절로 닫히며 Pinterest 탭으로 돌아와 로그인 상태가 되는지.
2. **탭 줄 모양** — 고른 탭 구분이 밝은·어두운 화면 모두에서 보이는지, 탭이 많을 때 트랙패드로 옆 스크롤이 되는지(마우스 휠 세로 굴림은 옆으로 넘기지 않는다).
3. **⌘클릭** — 검색 결과의 새 창 링크를 ⌘클릭하면 뒤 탭으로 열리는지(합성 이벤트로만 확인).
4. **다시 켜기** — 탭 서넛을 열고 하나를 고른 채 종료 → 다시 켜 웹 패널을 열면 탭들이 돌아오고 고른 탭만 불러오는지. 예전 버전에서 올라온 경우 마지막 주소가 탭 하나로 열리는지.
5. **뒤 탭의 소리** — 영상 탭을 연 채 다른 탭을 고르면 소리가 멈추고 돌아오면 다시 나는지.
6. **저장 중 탭 닫기** — 큰 이미지를 우클릭 저장하자마자 그 탭을 닫아도 파일이 생기는지.

### 리뷰 수정(2026-11-22)

탭 구현 리뷰에서 나온 열 가지를 고쳤다.

- **새 탭 제한**: `javaScriptCanOpenWindowsAutomatically = false`여도 한 번의 클릭으로 `window.open`을 여러 번 부르면 `createWebViewWith`가 그만큼 온다(리뷰어가 확인, 창 다섯 → 다섯 번). 한 탭의 페이지는 1초에 새 탭 둘까지만 열고 나머지는 막으며 "이 페이지가 여는 새 탭을 더 열지 않습니다."를 한 번 알린다(그 탭에 새 페이지가 들어서면 다시 센다). 탭은 모두 30개까지 — 넘으면 새 창·+·보기 → 새 탭·`openTab`(이제 `Int?`) 모두 열지 않고 "탭이 너무 많아 새 탭을 열지 않습니다."를 알린다. 복원도 30개까지만.
- **닫기 규칙 바로잡기**: 연 탭 기록(`openerID`)이 영구라 ⌘·새 창으로 연 탭을 ✕로 닫아도 연 탭으로 튀었다. 연 탭으로 돌아가는 것은 페이지가 스스로 닫을 때(`window.close()`)뿐이고, ✕·`closeTab`은 요구서대로 그 자리의 다음 탭(없으면 앞 탭)이다.
- **보통 링크의 ⌘클릭·가운데 클릭**: Safari처럼 뒤의 새 탭으로 연다(원래 요청 그대로 실어 Referer 유지, 같은 제한). WebKit의 `buttonNumber`는 버튼 비트다 — 합성 클릭으로 왼쪽 1, 가운데 4를 확인했다(`NSEvent.mouseEvent`는 버튼 번호를 못 정해 테스트는 CGEvent 필드로 가운데 버튼을 만든다).
- **알림은 고른 탭 것만**: 뒤 탭의 불러오기 실패·지원하지 않는 링크·팝업 차단·카메라 거절·프로세스 종료 알림이 앞 탭의 것처럼 상태 줄에 떴다. 이제 고른 탭의 것만 낸다(뒤 탭 받기 거절과 새 탭 제한은 패널에 관한 것이라 늘 낸다). 프로세스가 끝난 탭은 다음에 고를 때 다시 불러온다(자동 테스트 없음 — 프로세스를 죽일 공개 API가 없다).
- **이미지 알림도 고른 탭 것만**: 뒤 탭 스크립트의 `contextmenu`가 앞 탭에서 방금 누른 이미지를 덮을 수 있었다. 보이는 탭만 손으로 누르고 끌 수 있으므로 `contextmenu`·`dragstart` 모두 고른 탭의 웹 뷰에서 온 것만 받는다(요구서 7번 "뒤 탭의 알림도 받는다"를 바꾼 것 — 테스트도 "뒤 탭 알림은 무시, 출발지 판정은 모든 탭"으로 고쳤다).
- **복원은 설정을 쓰지 않는다**: 복원이 끝난 뒤에 저장 표시를 켠다. 예전 마지막 주소를 옮긴 경우만(그 값은 이미 지웠으므로) 바로 쓴다. 그 뒤 고른 탭이 불러오기를 마치면 평소대로 정돈된 값이 저장된다.
- **탭 줄**: 복원 뒤 끝 탭이 아니라 고른 탭이 보이게 스크롤한다(새로 생긴 탭 중 고른 탭이 있으면 그 탭). 폭이 0인 배치에서는 보이기 요청을 남겨 둔다. 항목은 ✕ 밖 어디를 눌러도 고르고, 고른 탭은 사이드바 선택 행처럼 진한 바탕(`labelColor` — 밝은 화면 검정·어두운 화면 흰색)에 반전 글씨(`textBackgroundColor`)·semibold, 고르지 않은 탭은 얇은 테두리. 세로 휠 굴림은 옆으로 넘긴다. 테스트에서 알게 된 것: 화면에 없는 창에서는 `visibleRect`가 잘리지 않은 값을 돌려줘 보임 판정에 못 쓴다 — 탭 줄이 보이는 부분(`visibleItemsRect`)을 내주고 항목 `frame`과 비교한다.
- **테스트**: 위 각각 + 이상한 주소(`ftp:`·글)와 음수·넘치는 번호로 복원, ⌘로 뒤에 연 영상 탭은 고를 때까지 멈춤, 엔진 테스트의 시트 걷기가 창 없이 뜬 저장·열기 창도 닫는다.
- **결과**: `make build` 성공·경고 0(새로 컴파일해도 0), `make test` 129개 통과, `make test-ui` 172개 통과 — 두 번 실행해 두 번 모두 172개, 실패 0.

### 탭 — 재검토 뒤 마무리(같은 날)

- ⌘클릭·가운데 클릭은 사용자가 직접 연 것이라 "한 탭이 1초에 둘" 제한을 걸지 않는다(전체 30개 제한만 본다). 그 제한은 페이지가 여는 창에만 적용한다 — 직접 빠르게 세 번 눌렀을 때 "이 페이지가 여는 새 탭을 더 열지 않습니다."가 뜨던 것을 고쳤다.

- **남은 것**: ① 내려받기로 이어지는 링크를 ⌘클릭·가운데 클릭하면 뒤 탭에서 받기가 취소되고 빈 탭이 남는다(그냥 누르면 받아진다) ② 탭 항목의 접근성 표시(고른 탭 알림)가 VoiceOver에 전달되지 않는다 ③ 뒤에서 연 탭이 불러오기에 실패해도 알림이 없어 골랐을 때 빈 화면만 보인다 ④ 프레임 안 링크의 ⌘클릭은 새 탭으로 열리지 않는다.
- **작성자 확인 필요**(손으로만 볼 수 있는 것): Pinterest의 Google 로그인이 새 탭으로 열렸다 닫히며 로그인되는지 · 실제 가운데 클릭 · 탭 줄의 고른 탭 표시(밝은·어두운 화면) · 탭 줄 위 휠 스크롤 · 탭을 여럿 연 채 껐다 켰을 때 복원 · 영상 탭을 뒤로 보냈을 때 소리가 멈추는지.

## 2026-11-22 — 웹 버튼을 사이드바 토글 오른쪽으로

- 툴바의 웹 버튼(지구본)을 오른쪽 끝(AI 버튼 옆)에서 **사이드바 토글 바로 오른쪽**으로 옮겼다. 웹 패널이 사이드바 옆에 열리므로 여는 버튼도 같은 쪽에 둔다(작성자 요청). 목록 화면·뷰어 화면 모두 `[사이드바 토글][웹][뒤로] …` 순서다. AI 버튼은 오른쪽 그대로.
